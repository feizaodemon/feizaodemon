The problem

A spreadsheet loses history: when a status cell is overwritten, the timeline is gone, and saving a posting and applying to it end up as the same row. I wanted a tool that keeps every status change as an event, separates “saved” from “applied”, and captures a posting in one click without giving a browser extension broad access.

How it works

A pnpm monorepo: a Fastify API with Zod contracts, a React web app and a Manifest V3 extension, over SQLite with Drizzle. The domain layer has no database or framework dependency, and the application layer has no HTTP dependency. One Node process serves both the API and the built web app.

Key decisions

01

Jobs and applications are separate records

Chosen
A Job is a saved posting; an Application is one attempt at it. Saving a job never creates an application.
Instead of
One row per posting with a status column.
Trade-off
Two concepts to explain, but re-applying or applying through another channel works, and a second open application for the same job is rejected inside the transaction (HTTP 409).
02

A status snapshot plus an event, in one transaction

Chosen
current_status is a snapshot for lists; application_events is the source of truth for the timeline, statistics and calendar. Corrections append events instead of rewriting history.
Instead of
Updating the status in place.
Trade-off
One extra row per change, in exchange for a timeline that can always be traced.
03

Frozen specs and append-only migrations

Chosen
The DDL, API contract and import format were written and frozen before the code. A test checks that runtime migrations match the frozen DDL byte for byte.
Instead of
Letting the schema drift with the code.
Trade-off
A protocol change needs its own versioned document, but docs, code and tests can be checked against each other automatically, and old exports still import.
04

A narrow extension that only saves jobs

Chosen
The extension reads the current page only after a click (activeTab + scripting), shows a preview, checks for duplicates, and saves a job. Application status is only edited in the web app.
Instead of
, background scraping, cookie access, or editing applications from the popup.
Trade-off
You cannot advance an application from the job page, but there is one path for status changes and the extension needs only 3 permissions and one host.
05

Import with a preview, then one transaction

Chosen
CSV/JSON import first classifies every row as new, duplicate, possible duplicate or invalid; after confirmation it writes everything in one transaction with an idempotency key.
Instead of
Silent overwrite or automatic merging of possible duplicates.
Trade-off
One more step for the user; a preview expires after 15 minutes and goes stale if the data changes.

Results

I use it every day in place of a spreadsheet. CI runs the 420+ Vitest cases on every pull request, including the byte-for-byte migration check and a WCAG AA contrast test across light and dark themes. Real browser checks of the extension stay manual, because automation cannot stand in for a real toolbar click.

My part

A personal project: I designed and built it, and I run it.

Limits and what is next

  • Single user by design. Sharing with other people would need a separate decision with authentication, isolation and deletion in place first.
  • Direction tagging uses fixed keywords, so results may need a manual check.
