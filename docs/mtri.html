The problem

A gesture interface for a robot arm has two jobs that pull against each other. It should feel quick, but a wrong guess must never move the robot. The project also had to run the same way against a simulated Panda and a real Franka FR3, and keep working when the input came from a serial magnetic board instead of a mouse.

How it works

Recognition, confirmation, dispatch and execution are four separate ROS nodes. The recognizer only publishes ranked candidates. The dashboard publishes a label only after the operator confirms it. The dispatcher maps that label to a fixed task vocabulary and is the only node that can command the robot. A second mode, TELEOP, sends keyboard or board input through one C++ Cartesian core that drives both robots.

Key decisions

01

A DTW template bank, benchmarked against five alternatives

Chosen
Strokes are normalized, resampled to 64 points and ranked by DTW against 124 templates. Confidence and margin gates reject unclear input.
Instead of
Derivative DTW, windowed DTW, Protractor ($1), $P and feature k-NN, all implemented behind one interface and compared offline.
Trade-off
On clean data every method scores 100%. Under synthetic noise and rotation Protractor matches or beats DTW at about 1/200 of the cost; DTW holds up better on truncated strokes. The runtime stayed on DTW, and the comparison is documented rather than hidden.
02

A human confirmation step between recognition and motion

Chosen
Only the dispatcher publishes /colmag/task_command, and only after an explicit confirm. Candidates from an earlier sample cannot be confirmed for the current one.
Instead of
Letting a confident recognizer trigger the task directly.
Trade-off
Every task costs one extra click. In exchange, a misrecognition cannot move the robot. Bad dispatcher configuration now stops the node instead of silently falling back to a default mapping.
03

One C++ Cartesian core for simulation and hardware

Chosen
Fr3CartesianTeleopCore owns target filtering, damped-least-squares IK, workspace and joint bounds, and finite-output checks. The Gazebo Panda and the FR3 adapter both link it.
Instead of
Separate teleop code per backend.
Trade-off
Gazebo runs and the ROS-free C++ tests exercise the same code the FR3 route uses. Keyboard input was first routed through the board's point-to-point filter, which cruised at about 0.03 m/s and overshot about 11 cm on a direction change; it became a velocity command with acceleration and jerk limits.
04

Mode ownership is not hardware authorization

Chosen
A latched TASK/TELEOP mode decides which path owns the command. Switching mode never starts a backend or enables physical commands, and invalid mode state fails closed.
Instead of
A single “enable robot” toggle tied to the mode.
Trade-off
More states to reason about, but the CI Gazebo smoke test checks the gating on every pull request: TASK rejects gripper commands, TELEOP moves, TASK rejects again.

My part

The repository is my portfolio copy of a collaborative project. My parts: the board orientation clutch and the board and mouse profiles; the DTW recognition path, gates, tracked bank and evaluation tools; the shared dashboard and confirmation flow; integration of the dispatcher, Gazebo bridge and FR3 adapter; TASK/TELEOP ownership and the shared Cartesian core; Docker packaging, CI and tests; and the architecture, safety and validation docs.

Limits and what is next

  • All 124 templates were drawn with a mouse by one person. The accuracy is an upper bound for one writer, not a measured accuracy for new users or for the magnetic board.
  • The robustness perturbations are synthetic; real board error has not been recorded.
  • The Real-FR3 adapters compile and are in the launch graph, but physical Real-FR3 TELEOP has not been run.
  • Next: collect strokes from other writers and on the board, then re-run the same evaluation.
