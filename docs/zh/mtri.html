要解决的问题

机械臂的手势交互有两个相互牵制的目标：要反应快，但识别错了绝不能让机器人动。同一套系统还要既能接 Gazebo 里的仿真 Panda，也能接真实的 Franka FR3，而且输入既可以是鼠标，也可以是串口磁性画板。

系统结构

识别、确认、调度、执行是四个独立的 ROS 节点。识别节点只发布排序后的候选；仪表盘只有在操作员确认后才发布标签；调度节点把标签映射到固定的任务表，并且是唯一能给机器人下指令的节点。另一个模式 TELEOP 把键盘或画板输入送进同一个 C++ 笛卡尔核心，由它驱动两台机器人。

关键设计决策

01

DTW 模板库，并与 5 种替代方法对比

选择
笔迹归一化、重采样为 64 点后，与 124 个模板做 DTW 排序；置信度和差距门限拒绝不清楚的输入。
放弃
导数 DTW、加窗 DTW、Protractor（$1）、$P、特征 k-NN，全部用同一接口实现并离线对比。
取舍
干净数据上所有方法都是 100%。在合成噪声和旋转下，Protractor 与 DTW 持平或更好，耗时约为 1/200；截断笔迹上 DTW 更稳。运行时仍用 DTW，对比结果如实写进文档。
02

识别和运动之间必须有人确认

选择
只有调度节点发布 /colmag/task_command，而且必须在明确确认之后；上一笔的候选不能被确认到当前这一笔上。
放弃
让高置信度的识别结果直接触发任务。
取舍
每个任务多一次点击，换来误识别无法单独让机器人运动。调度配置写错时节点会直接停止，而不是悄悄退回默认映射。
03

仿真和真机共用一个 C++ 笛卡尔核心

选择
Fr3CartesianTeleopCore 负责目标滤波、阻尼最小二乘逆运动学、工作空间与关节限位、输出有限性检查；Gazebo Panda 和 FR3 适配器都链接它。
放弃
每个后端各写一套遥操作代码。
取舍
Gazebo 运行和不依赖 ROS 的 C++ 测试覆盖的就是 FR3 路线用的同一份代码。键盘输入最初走画板的点到点滤波，巡航速度约 0.03 m/s，换向时过冲约 11 cm；后来改成带加速度和加加速度限制的速度指令。
04

模式切换不等于授权硬件

选择
锁存的 TASK/TELEOP 模式只决定哪条路径拥有指令权；切换模式不会启动后端，也不会开启实机指令；模式状态无效时按关闭处理。
放弃
用一个与模式绑定的“启用机器人”开关。
取舍
需要考虑的状态更多，但 CI 中的 Gazebo 冒烟测试每个 PR 都会验证：TASK 下拒绝夹爪指令，TELEOP 下可以运动，切回 TASK 再次拒绝。

结果

指标结果
124 个模板、8 个符号的留一法评测Top-1 100%，Top-3 100%
通过运行时门限的查询100%，全部正确
识别耗时（纯 Python DTW）中位数 83 ms，p95 118 ms，单核
鲁棒性：DTW 对比 Protractor（噪声 σ=0.12 / 旋转 45° / 截断 30%）95.2 / 84.1 / 38.7% 对比 100 / 100 / 18.5%
自动化检查约 590 个 pytest 用例、7 个 C++ 测试程序，CI 含无界面 Gazebo 冒烟测试

我负责的部分

这个仓库是一个合作项目的作品集版本。我负责的部分：画板的方向离合和画板/鼠标两套交互配置；DTW 识别路径、门限、模板库和评测工具；共用仪表盘和确认流程；调度节点、Gazebo 桥接和 FR3 适配器的集成；TASK/TELEOP 指令权和共用笛卡尔核心；Docker 打包、CI 和测试；以及架构、安全和验证文档。

局限与下一步

  • 124 个模板全部由同一个人用鼠标画出。准确率只是单人数据上的上限，不代表新用户或磁性画板上的实际准确率。
  • 鲁棒性评测里的扰动是合成的，还没有录制真实画板误差。
  • 真机 FR3 适配器能编译，也在 launch 图里，但真机 TELEOP 还没有实际运行过。
  • 下一步：收集其他人和画板上的笔迹，用同样的评测脚本重新测一遍。
