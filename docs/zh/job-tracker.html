求职工作台

自己部署、每天在用的求职管理工具，替代了 Excel 表格，配一个能从正在看的招聘页保存岗位的 Chrome 扩展。

私有仓库。本页只介绍工作内容，不公开代码。

要解决的问题

表格会丢历史：状态单元格一改，时间线就没了；“收藏了岗位”和“已经投递”也挤在同一行里。我想要一个工具：每次状态变化都保留为事件，把“已保存”和“已投递”分开，并且能一键保存岗位，同时不给浏览器扩展过大的权限。

系统结构

pnpm monorepo：Fastify API 配 Zod 契约、React 网页、Manifest V3 扩展，数据存在 SQLite（Drizzle）。domain 层不依赖数据库和框架，application 层不依赖 HTTP；一个 Node 进程同时提供 API 和构建好的网页。

关键设计决策

01

岗位和投递分开存

选择
Job 是保存的岗位，Application 是针对它的一次求职流程；保存岗位绝不隐式创建投递。
放弃
每个岗位一行，用一列表示状态。
取舍
多了一个概念，但可以重新投递或换渠道投递；同一岗位已有进行中的投递时，第二次创建会在事务内被拒绝（HTTP 409）。
02

状态快照和事件在同一事务里写入

选择
current_status 是给列表用的快照；application_events 是时间线、统计和日历的事实来源。更正也是追加事件，不改写历史。
放弃
直接原地改状态。
取舍
每次变化多写一行，换来永远可追溯的时间线。
03

冻结规格，migration 只追加

选择
DDL、API 契约和导入格式先写成文档并冻结，再写代码；测试会检查运行时 migration 与冻结的 DDL 逐字节一致。
放弃
让 schema 跟着代码随意变化。
取舍
改协议要单独出一版文档，但文档、代码和测试之间可以自动核对，旧的导出文件也仍能导入。
04

权限很窄、只保存岗位的扩展

选择
扩展只有在用户点击后才读取当前页面（activeTab + scripting），先预览、查重，再保存岗位；投递状态只在网页里修改。
放弃
<all_urls>、后台抓取、读取 Cookie，或在弹窗里直接修改投递。
取舍
不能在招聘页上直接推进投递，但状态变化只有一条路径，扩展也只需要 3 个权限和一个 host。
05

导入先预览，再单事务写入

选择
CSV/JSON 导入先把每行分成新建、完全重复、疑似重复、无效；确认后带幂等键在一个事务内全部写入。
放弃
静默覆盖，或自动合并疑似重复。
取舍
用户多一步确认；预览 15 分钟后失效，数据变化后旧预览也会失效。

结果

我每天都在用它替代表格。CI 在每个 PR 上运行 430+ 个 Vitest 用例，包括 migration 逐字节校验，以及浅色/深色主题下的 WCAG AA 对比度测试。扩展的真实浏览器检查保留为人工验收，因为自动化无法代替真实的工具栏点击。
